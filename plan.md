# rsbsky: Rust/Ratatui port of bskyban

## Context
`../bskyban` (Go, Bubble Tea, ~8.2k LOC) is a Bluesky TUI for reviewing followers, browsing the home timeline, and moderating (block/follow/keep). It uses plain XRPC REST polling with an app password. There is no firehose, DB, or config file. `rsbsky` is an empty git repo. Goal: a behavior-compatible Rust port, built incrementally, **starting with the feed view**, keeping the **CLI flags and environment variables identical** so it works as a drop-in replacement (same state/audit files too).

This document is a plan only. Scaffolding, dependency installation, code, tests, and CI begin only when implementation is separately requested. During implementation, incomplete milestones are not yet drop-in replacements; supported commands and temporary stubs must be documented.

## Stack
`ratatui` + `crossterm`, `tokio`, `reqwest` (rustls, 30s timeout), `serde`/`serde_json`, `clap` (derive + env; idiomatic Rust CLI syntax, see Phase 0), `humantime` (durations), `unicode-segmentation` + `unicode-width`, `anyhow`/`thiserror`, `directories`-free XDG logic (hand-rolled to match Go). Tests: `wiremock` (fake PDS, equivalent to `internal/testpds`), `insta` or ratatui `TestBackend` for render snapshots.

## Layout
```
src/main.rs        dispatch, exit codes (0 ok, 1 err, 2 usage)
src/cli.rs         flags, UsageText, env resolution
src/bsky/          client.rs (XRPC, createSession), feed.rs, post.rs, profile.rs, records.rs
src/store/         state.rs (state.json), audit.rs (audit.jsonl)
src/app/           is_new, feed_candidates, create_for/delete_for
src/tui/           app.rs (event loop), feed.rs, theme.rs, widgets (osc8, wrap), later: review, picker, follows, compose
src/termtext.rs    sanitize (strip ANSI/control), OSC 8, grapheme wrap
tests/             wiremock-based integration tests
```

## Compatibility contract (fixed in Phase 0, honored throughout)
- Env: `BSKY_HANDLE`, `BSKY_APP_PASSWORD` (required except `log`/`themes`/`help`), `BSKY_PDS` (default `https://bsky.social`), `BSKYBAN_STATE`, `BSKYBAN_AUDIT`, `XDG_STATE_HOME` (only if absolute; else `~/.local/state/bskyban`), `BSKYBAN_FANCY` (1/true/yes, ORed with `--fancy`), `BSKYBAN_THEME` (default `auto`, `--theme` overrides), `BROWSER` (else `open`/`xdg-open`), `NO_COLOR`.
- Commands: `feed` (default when no command or first arg starts with `-`), `review`, `posts`, `list`, `log`, `themes`, `baseline`, `show`, `block|unblock|follow|unfollow [--dry-run] (ids|-)`, `keep`, `post`, `delete-post`, `like|unlike`, `help|-h|--help`.
- Feed flags: `--pages N` (3), `--backlog`, `--refresh DUR` (30s; 0=off; else >=10s or usage error exit 2), `--fancy`, `--theme`, `--list`, `--json` (JSON Lines: did, handle, displayName, repostedBy, text).
- CLI syntax is idiomatic clap, not a clone of Go's `flag` package: `--flag value`/`--flag=value`, `-h/--help` generated by clap, `--` per POSIX, bool flags are plain switches, durations via `humantime` (`30s`, `1m`, plus bare `0`). Differences from Go syntax (e.g. `-list` single-dash long flags, `--list=false`, usage/error wording) are intentional and listed in `docs/compat.md`. **Preserved exactly:** the environment variables above, command names and their meaning, flag names, defaults and bounds (`--refresh` 0 or >=10s, `--pages` 3), exit codes (0/1/2), `feed --json` / `posts --json` headless exceptions, and "unknown explicit theme => exit 2".
- Order: `log`, `themes` and help never need credentials; `feed`/`posts`/`review` validate options before credentials/login (clap does this naturally); other commands check credentials, load state and log in before running. An unknown command is a clap usage error (exit 2) without logging in (deliberate improvement over Go, which logged in first).
- Printed lists ignore `BSKYBAN_THEME`; `posts --json` is headless, while `feed --json` alone still launches the TUI.
- Files: `state.json` (`{"entries":{did:{handle,decision,at}}}`) and append-only `audit.jsonl` use Go-compatible schemas and must be mutually readable. Match missing/null entries handling, omitted audit fields versus explicit zero/false values, timestamp formats/precision, and malformed-file errors. State writes use atomic tmp+rename and roll back in-memory changes on save failure; match Go's 0700 directory/0600 file creation modes on Unix. Existing-directory/file permission behavior must be captured in fixtures.
- File compatibility means equivalent parsed values and successful round trips, not identical JSON key order, whitespace, or escaping. Preserve array/event order and timestamp values when reading and rewriting entries. CLI plain-text output, usage, stdout/stderr routing, and exit codes require exact fixture comparisons; JSON Lines require equivalent parsed objects in the same row order. Only normalize explicitly identified dynamic fields, such as generated timestamps and server record IDs, while checking their format and relationships separately.
- Shared files support sequential use by either tool. Concurrent state writers are outside the compatibility guarantee: atomic rename does not prevent lost updates. Any stronger concurrency guarantee or other deliberate departure from Go requires an explicit contract change.

## Phases

### Phase 0: Scaffold & CLI/env compatibility
- Before implementation, identify the reference Go commit and record any dirty-source differences used as the baseline. Keep the baseline fixed through parity verification; source changes require an explicit fixture update.
- `cargo init`, deps, CI (fmt, clippy, test).
- Implement `cli.rs` dispatch, all command/flag definitions, env/XDG path resolution, theme-name validation, and help/usage text. Unimplemented command bodies print "not yet implemented" with exit 1; these temporary exceptions must be listed, including any login/state checks not yet available, rather than counted as parity passes.
- Build an executable compatibility matrix from the Go binary: environment, initial files, stdin, terminal versus pipe, stdout, stderr, exit status, and expected login/API calls. Cases are written in the Rust CLI's syntax with a Go-syntax translation; cover absent credentials, refresh/pages bounds, theme precedence/headless exceptions, and empty/relative/absolute XDG overrides. Pure syntax differences are documented rather than matched.
- Capture Go-generated state/audit fixtures, including missing/empty/null/malformed data, Unicode, timestamp precision, and optional/zero-valued fields. Fix fixture time, API responses, and generated IDs where practical.
- Exit: help, supported dispatch/validation paths, and path resolution match the baseline. The matrix names deferred cases and the phase that will enable them.

### Phase 1: API client, state reading & headless repost candidates
- `createSession` with handle/app password → `accessJwt` Bearer (no refresh, matching Go). Error format `nsid: message (error)`.
- `getTimeline` with caller-supplied limit/cursor: Following uses 50 items per page; repost candidate scanning uses 100. Match Go's minimum-one-page behavior for candidate scans. `getProfile(s)`. Post model parsing embeds: images, video, external, record, recordWithMedia; `reasonRepost`; reply parent; viewer follow/block state; authenticated DID/handle.
- Implement `store::state` reading and `app::{is_new, feed_candidates}` now. `feed --list` returns eligible original authors of reposts, not the Following timeline: exclude self/followed/blocked/decided authors, include skipped decisions only with `--backlog`, retain first-appearance order and first post per author, and aggregate distinct reposter handles in order.
- Implement text sanitization for remote content and errors before terminal output. Keep raw JSON text behavior compatible with Go; add generated ANSI/OSC only after sanitizing terminal content.
- Use scripted fake PDS fixtures to replay identical responses to both binaries with separate copies of the same initial state. Port relevant Go `bsky`, state-load, app filtering, and CLI output cases; include pagination, duplicates, empty pages, and API errors.
- Exit: `rsbsky feed --list [--json]` matches the baseline on deterministic fixtures, including saved decisions and backlog. Request traces confirm authentication, page sizes/cursors, and no remote mutations or state writes. A live read-only run is a smoke check, not the parity oracle.

### Phase 2: Feed view TUI (first UI milestone)
- Alternate-screen ratatui app, async event loop (crossterm `EventStream` + tokio tick + HTTP result channel).
- Terminal lifecycle: restore raw mode, cursor, and alternate screen after normal quit, Ctrl+C, partial initialization failure, runtime error, and unwinding panic. Cancel outstanding requests/tasks on shutdown; slow HTTP must not prevent input, redraw, or prompt quitting. Define ownership of UI state and guard against overlapping loads or stale results.
- Following list: up to 3 text lines, quoted post (2 lines, `▎`), `↻ reposted by @who · written 8m ago`, `↳ replying to @who` (indent for same-thread replies), age as OSC 8 link to bsky.app, link cards `↗ Title url`, image marker `▣`, key-hint bar, scrolling with cursor-pagination load-more near the end.
- Keys: ↑/↓, PgUp/PgDn, `R`, `q`/ctrl+c. Themes (`auto,dark,light,ansi,dracula,catppuccin`, `NO_COLOR`), `themes` preview command.
- Refresh: `--refresh 0` disables background checks. Otherwise check up to 4 Following pages, stopping after a page overlaps known items or the cursor ends. Identity matches Go's post URI plus reposter handle, so the same post from two reposters remains two entries. Deduplicate against both displayed and pending items; preserve ordering and report a gap when the scan limit is reached without overlap.
- Insert background results immediately whenever the reader is at the unobstructed top of Following; otherwise hold them with `Following (+N new)`. `R` inserts waiting posts without another fetch and jumps to the top; with none waiting it starts a check, or requests application of an already-running check. Preserve selection while holding results. Once detail/composer/busy states exist, they must prevent automatic insertion as in Go.
- Background failure shows `⚠ refresh failed`; manual failure is visible as an error; successful checks clear the background warning. Bring the minimal `store::audit` writer forward to this phase: audit a persistent background error once until it changes or clears, and audit every manual failure, with Go-compatible source/detail fields. Fancy mode: highlight bar + `new` tag fading over 2s with an 80ms tick.
- OSC 8 spike at the start of the phase: establish a rendering strategy compatible with ratatui's cell buffer and redraws. Validate link boundaries/widths after scroll, resize, and partial redraw; raw escapes in cell symbols or a post-draw pass are candidates to investigate, not assumed solutions. Resolve the strategy before building dependent widgets; retain a testable non-link terminal fallback.
- Tests: `TestBackend` snapshots for layout/wrap/new-indicator, deterministic clock and scripted-result tests for refresh ordering, deduplication, gap reporting, `R` during requests, error auditing, and animation. PTY/manual checks cover terminal restoration and quitting during slow requests; snapshots do not establish these properties.
- Exit: read-only Following navigation, pagination, refresh, themes, and link rendering pass fixture and terminal checks; refresh audit events round-trip through Go's reader.

### Phase 3: Post detail view
- `→`/`←`/`Esc`: two-panel layout (profile left, post right), counts, parent/quoted post, image links, author's recent posts (`getAuthorFeed posts_with_replies`), profile stats (age, posts/day, follower ratio, follows-you). Next/prev post navigation, panel scroll.
- Link picker (Enter/o) and `i` open images, using `BROWSER`/`open`/`xdg-open`.

### Phase 4: State writing, audit reading & moderation actions
- Extend the earlier state reader/audit writer with state persistence, audit reading and `log`, and `app::{create_for, delete_for}`. Keep `log` credential-free. Port Go's missing/malformed audit-file behavior and persistence error handling.
- Feed actions: `b` (confirm if followed), `f`, `k`, `u` (confirm), `U` undo, `F` follows browser. Headless commands: `block/unblock/follow/unfollow/keep/baseline/show/log/list` incl. `--dry-run`, stdin `-`, audited with `source` = `cli` or `tui:*`.
- Model remote completion separately from local persistence. If a remote action succeeds and saving fails, retain its result/record URI, show that the action completed, block conflicting TUI actions, and let `r` retry only the local save. Preserve Go's quit behavior while an action/save is pending. Match CLI reporting and audit warnings separately from TUI recovery behavior.
- Undo restores the prior decision and required remote relationship. Restoring a deleted relationship produces a new record URI; update earlier undo entries so a later undo deletes the replacement record. Retain undoability after remote failure and distinguish partially completed relationship transitions.
- Failure-injection tests: remote failure; remote success then save failure; repeated local save retries without another mutation; audit append failure; undo failure; block/follow transitions and replacement URI tracking; already-followed/blocked and absent-record cases. Verify state rollback and the resulting audit events.
- Exit: deterministic fake-PDS mutations and sequential Go→Rust/Rust→Go file round trips pass. Dry runs make no remote mutations or decision changes but append the expected audit events; they do not count as state-write coverage.

### Phase 5: Reposts tab & Review
- Tab switching; Reposts tab reuses Phase 1 candidate filtering. New eligible authors from refresh append without moving the selected candidate; existing authors accumulate distinct reposters. `review` command (one follower at a time; `b f k s u U r q`, Home/End, handled-state badges, `--since`, `--backlog`).
- Exit: tab/selection, filtering/backlog, refresh merging, and review mutation/recovery behavior match Go fixtures and relevant TUI tests.

### Phase 6: Writing posts & `posts` view
- Composer (300-grapheme counter, facets for links, reply root/parent threading, keeps text on failure), like/unlike `h`, delete own post `d`, `post`/`delete-post`/`like`/`unlike` CLI, `posts` command.
- Exit: deterministic fake-PDS request/output/audit cases cover successful and failed writes, Unicode facet byte offsets, reply threading, own-post validation, input retention after failure, and the CLI/headless exceptions from Phase 0. Apply the refresh insertion guards for an open composer/detail view.

### Phase 7: Polish & parity
- Complete the cross-tool fixture harness introduced in Phase 0, analogous to `scripts/smoke.sh`, with isolated temp directories, fake-PDS mutations, file round trips, and explicit normalization rules. Keep live smoke checks read-only or `--dry-run`, with audit paths redirected to temporary files.
- README, release builds, supported platform/toolchain documentation, and final terminal checks. Avatar/inline-image rendering is an optional post-parity enhancement; Go opens images in the browser.
- Exit: every compatibility-matrix case is enabled and passes, temporary command stubs are removed, and no unexplained behavioral deviations remain.

## Reference files (Go)
Paths are relative to the fixed `../bskyban` baseline: `cmd/bskyban/main.go` and `main_test.go` (dispatch and validation), `internal/cli/cli.go` and `logcmd.go` (usage/commands), `internal/tui/ui.go` and `tui.go` (feed, page sizes, keys, refresh, mutation recovery), `internal/tui/{refresh,audit,follow,fancy}_test.go`, `internal/tui/theme.go`, `internal/bsky/*`, `internal/store/*`, `internal/app/app.go`, `internal/termtext`, `internal/testpds`.

## Verification
- Per phase: `cargo fmt --check && cargo clippy -- -D warnings && cargo test`.
- Cross-tool comparisons use identical scripted PDS responses, fixed initial files, controlled time/IDs where practical, and isolated copies of environment/state. Compare exact plain output/status/routing and parsed JSON as defined in the contract; assert request traces as well as output.
- Phase 1-2: verify headless candidates with existing decisions, Following pagination/refresh, render snapshots, and refresh audit compatibility. Sequential live-feed diffs are diagnostic only because the feed can change between requests.
- Phase 4+: run actual mutations against the fake PDS and inspect requests, decisions, and audits. Write with Go and read with Rust, then reverse; include Rust state changes that Go subsequently reads and updates. Separately verify dry-run behavior and failure-injection cases.
- PTY/manual TUI checks in a real terminal (tmux): OSC 8 links across redraw/scroll, Unicode widths, small windows/resize, NO_COLOR, startup/runtime failure cleanup, Ctrl+C, and quitting with slow requests. Keep live-account checks read-only and use temporary state/audit paths.
- Update the compatibility matrix at every phase; deferred cases remain visibly incomplete until their implementation passes. No parity claim rests solely on snapshots, dry runs, or a changing live account.
